# Gradle auto-configuration from Scanner CLI: reuse the Gradle plugin or read Tooling API models?

**Investigation date:** 2026-10-12  
**Inputs:** [SCANENGINE-752](https://sonarsource.atlassian.net/browse/SCANENGINE-752), [PR #734](https://github.com/SonarSource/sonar-scanner-engine/pull/734), the local POC branch `avi/gradle-tooling-api-models-POC`, and the current `sonar-scanner-gradle` checkout. The Jira issue redirects to an Atlassian login here, so its private description and comments could not be verified. PR #734 is closed without merge; the local branch contains the POC and may include later edits.

## Short answer

The shared scanner engine does **not** imply shared Gradle discovery. Today the Gradle plugin is a Gradle build participant: it reads the project's Gradle model, creates tasks, computes Sonar properties, and then bootstraps the scanner engine. Scanner CLI starts the engine without that Gradle context. Calling the plugin from the engine therefore means starting **another Gradle invocation**, applying compatible plugin code to the target build, running an export-only action, and returning its data to the already-running engine. Calling the regular `sonar` task would start a second analysis.

The POC's Tooling API route avoids requiring Sonar's Gradle plugin in the target build. It correctly retrieves real project paths, directories, source buckets, and many dependencies. But the built-in IDEA and Eclipse models do not provide several Sonar-critical values, notably real compiler output, test/JaCoCo report locations, and a consistent definition of tests. The POC is a model-dump experiment, not an integrated Gradle auto-configuration implementation.

**Recommendation:** use the Tooling API as the CLI-to-Gradle transport, but test a **Sonar-owned, versioned Gradle model/export adapter** before maintaining an independent IDEA/Eclipse-to-Sonar property mapper. Extract Gradle-independent aggregation/property rules into a small shared library or wire protocol used by both products. Keep the Gradle-facing extraction inside Gradle. This is a third option: it reuses semantics without making the scanner engine depend directly on the Gradle plugin or making the plugin open a nested Tooling API connection.

## The three realistic designs

| | A. Invoke the existing Gradle plugin in export mode | B. Built-in Tooling API models, as in the POC | C. Tooling API + Sonar-owned Gradle model/export adapter |
| --- | --- | --- | --- |
| Flow | CLI engine launches target Gradle; applies Sonar plugin; runs a **new** export-only task; reads serialized properties; continues current analysis. | CLI engine connects to target Gradle and requests `GradleProject` plus `IdeaProject` or `EclipseProject`; maps them to Sonar properties itself. | CLI engine connects to target Gradle and requests/executes a Sonar model builder or export action; Gradle-side adapter extracts data; engine maps a stable DTO to analysis. |
| Strongest benefit | Highest chance of matching the existing plugin's Java/Android/Kotlin semantics and user-defined Sonar DSL. | No Sonar plugin application or artifact injection; good for transparent opt-in CLI enrichment when the build can supply standard IDE models. | One Gradle-facing extraction and one testable contract; CLI uses supported Tooling API transport. |
| Main cost | Export-only mode, plugin distribution/injection, version pinning, build modification, and nested scanner-engine/Gradle lifecycle. | A second, incomplete Gradle interpretation; IDE model conventions and third-party customizations become Sonar behavior. | New adapter, serialization/protocol versioning, distribution/injection, and compatibility testing across target Gradle versions. |
| Isolation and Configuration Cache | Export task must obey both; current local isolated mode requires applying the plugin in every project. | A Tooling API model request does not bypass target-build isolation rules; IDEA/Eclipse behavior under Isolated Projects is untested in this POC. | Adapter must be designed and tested for isolation and Configuration Cache; can reuse the plugin's per-project data flow rather than reintroduce root cross-project reads. |
| Likely first use | Existing users who already apply a compatible Sonar Gradle plugin; explicit export mode. | Narrow best-effort defaults (project tree, existing source paths, selected classpaths) with clearly lower fidelity. | Long-term common high-fidelity route if injection and compatibility are acceptable. |

### Why “just call the plugin” is more work than it sounds

The current Gradle task [bootstraps and calls the engine](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/java/org/sonarqube/gradle/SonarTask.java:699). The engine cannot safely invoke that task to obtain configuration, because the task would bootstrap another engine and analyze a second time. A Gradle-plugin route needs an export-only task or model that stops before engine bootstrap. The Maven auto-config reader provides a useful precedent: it [runs the Maven Sonar plugin in dump mode](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/shared/build-system-auto-config/src/main/java/org/sonar/scanner/buildsystem/maven/MavenBuildSystemModelReader.java:27), parses the file, and continues the CLI analysis.

For Gradle, the CLI also needs a way to select/install a compatible plugin version, expose it to the target build without unexpectedly changing the user's scripts, decide whether to honor an already-applied version and its `sonar { ... }` configuration, pass analysis-root and property overrides, isolate credentials, and prevent export from triggering compilation or a second scan. A Tooling API `BuildAction`, model builder, init script, or dedicated task could carry the request, but each changes packaging and compatibility. The current isolated mode [requires local application in every contributing project](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/README.md:99); a root-only injected plugin cannot assume it can configure children.

### What the built-in Tooling API route really buys

The POC connects through [`GradleConnector`](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/src/main/java/org/sonar/scanner/poc/gradle/GradleBuildProbe.java:39) and requests `BuildEnvironment`, `GradleProject`, `IdeaProject`, and `EclipseProject`. It neither runs a target-project task nor calls the scanner engine. Gradle's official [Tooling API documentation](https://docs.gradle.org/current/userguide/tooling_api.html) confirms that the API is wrapper-aware, can query project/dependency/source models, and always uses a daemon.

The POC observed:

- The target wrapper selected Gradle 9.7.1 while the client library was 9.8.0. A wrapper-less build silently used the client version instead, so a production reader needs an explicit fallback policy. [POC notes](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:61)
- Project paths and renamed project directories came back correctly. Sources/tests and many classpath entries were visible. No target-project task ran, though `buildSrc` tasks **did** run. [POC notes](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:63)
- Neither built-in IDE model exposed actual compiled output directories for `sonar.java.binaries`; neither supplied test/JaCoCo report paths. The Eclipse outputs shown were Eclipse-specific `bin/...` paths, not Gradle's `build/classes/...`. These are functional gaps, not merely mapper omissions. [POC notes](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:89)
- IDEA and Eclipse disagreed on test fixtures and which nonexistent source directories to report. Third-party plugins can modify both IDE models; one fixture had paths in both production and test buckets. IDEA dependency resolution also carried source jars that analysis does not need. [POC comparison](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:156)
- Plain model requests configured included builds but did not return their project models. Composite support needs explicit traversal or a build action. The POC did not test Android, Kotlin/Groovy, offline, Configuration Cache, or Isolated Projects. [POC limits](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:127)
- On the measured 54-project build, a warm `GradleProject` request took about 27–29 seconds and `IdeaProject` another 8–12 seconds; a cold `GradleProject` request took about 100 seconds. These are one-machine observations, not a general performance forecast. [POC timings](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/poc/gradle-tooling-api/README.md:117)

The built-in models are a good discovery baseline. Treating them as equivalent to the Gradle plugin's analysis properties would be a product behavior change, especially for Java binaries, Android, reports, and nonstandard source sets.

## Can a common dependency remove duplication?

Yes, if its boundary is chosen carefully. A useful shared artifact would contain **no Gradle `Project`, task, Tooling API, or scanner-engine bootstrap types**. It could define a versioned `GradleAnalysisModel`/serialization contract and pure rules for module hierarchy, skip semantics, path normalization, and conversion to Sonar properties. The plugin's Gradle adapter would produce the model; the CLI reader would consume it and feed the existing [build-system auto-config registry](/Users/alban/dev/github/SonarSource/sonar-scanner-engine/shared/build-system-auto-config/src/main/java/org/sonar/scanner/buildsystem/BuildSystemModelRegistry.java:48).

That artifact does **not** eliminate Gradle-specific extraction. Sources, variants, classpaths, compiler outputs, and reports still need code running against the target Gradle build, whether in the existing plugin, a small companion model builder, or both. If the engine depends directly on `sonar-scanner-gradle`, it imports a Gradle-runtime-shaped component into the engine, enlarges the downloaded engine and its classpath, and still cannot execute the plugin without a Gradle connection. It also creates an awkward release and layering relationship: today the Gradle plugin depends on scanner library/bootstrap APIs and [calls the engine](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/java/org/sonarqube/gradle/SonarTask.java:699).

The current local Gradle plugin already has promising pieces for an export protocol: [`sonarMetadata` writes project-local metadata](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/java/org/sonarqube/gradle/SonarMetadataTask.java:34), and the isolated path [publishes metadata and resolver artifacts](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/java/org/sonarqube/gradle/SonarQubePlugin.java:360). These are local branch code, not proof of a released public protocol. They contain per-project information; the CLI would still need a stable aggregate export, schema/version negotiation, and a way to request it without running `sonar`.

## Would the Tooling API simplify sonar-scanner-gradle?

**As a direct replacement for the plugin's Gradle API: probably not.** The plugin is already *inside* the build. It has direct access to source sets, Android variants, task outputs, configurations, providers, and task dependencies. The Tooling API is a client interface for a process *outside* the build. Having the plugin open a Tooling API connection to its own build would add a nested Gradle invocation, daemon, duplicate configuration and dependency resolution, and possible locking/lifecycle problems. It would lose the useful provider/task wiring that the plugin already has. Built-in models also omit information the plugin currently provides.

The Tooling API can simplify **the CLI integration**: it chooses the target wrapper, provides structured model requests, cancellation, progress, and standard daemon management. A **custom** model builder could reduce duplication by exposing Sonar's own data rather than reverse-engineering IDEA/Eclipse models. That still requires Gradle API code on the build side. It should not be sold as eliminating Gradle-version breakage or project isolation work.

The local Gradle checkout demonstrates both progress and remaining complexity. It now has a Gradle 9.7 isolated path with per-project metadata/variant artifacts and Java, Android, and Kotlin JVM fixtures, but still maintains a separate legacy path and uses a [Gradle internal `StartParameterInternal` API](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/java/org/sonarqube/gradle/SonarQubePlugin.java:289). A shared model can reduce duplicated Sonar mapping rules; it cannot remove the need to maintain those Gradle-facing adapters.

## Version support is a product choice, not a single API number

| Dimension | Plugin export route | Built-in Tooling API route | Custom model route |
| --- | --- | --- | --- |
| Target Gradle version | Bounded by the chosen Sonar Gradle plugin release and its runtime/API compatibility. Published plugin docs say **Gradle 7.3+**; this checkout's QA matrix additionally tests 5.6.4 and 6.8.3, which is broader test evidence, not the published promise. | Gradle says a 9.x Tooling API client is guaranteed to run target Gradle **4.0+** (last five major releases). That is transport compatibility; individual model getters may be unavailable and target builds may require older JDKs. | Limited by **both** Tooling API transport and the custom build-side adapter/plugin's compiled API and JVM requirements. A 9.8 client alone does not make a 9.8-built model builder run on Gradle 4. |
| Java runtime | Target Gradle daemon must use a Java version it supports; current Sonar Gradle docs specify Java 17 for plugin use. | The Tooling API client and target daemon can run on different JVMs, but the daemon must match target Gradle and build plugins. The scanner engine's Java requirement does not magically satisfy an old wrapper. | Same separation, plus model-builder bytecode must be loadable by the oldest target daemon/JVM. |
| Isolated Projects | Current local plugin implementation targets Gradle **9.7+** and requires application in every project; the non-isolated root-only path remains separate. | The POC did not exercise Isolated Projects. A model request still configures the target build and can encounter isolation violations in build logic or model builders. | Explicitly design and test per-project model building/aggregation under 9.7+; older Gradle needs a compatible path. |
| No wrapper | Existing plugin works when invoked by an installed Gradle. | The POC's connector falls back to its client version; requiring a wrapper is a **proposed product restriction**, not a Tooling API requirement. | Same transport choice as the Tooling API route. |

Sources: [Gradle Tooling API compatibility](https://docs.gradle.org/current/userguide/tooling_api.html#sec:embedding_compatibility), [Gradle Java compatibility](https://docs.gradle.org/current/userguide/compatibility.html), [Isolated Projects constraints](https://docs.gradle.org/current/userguide/isolated_projects.html), [plugin prerequisites](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/src/main/resources/static/documentation.md:10), [local QA matrix](/Users/alban/dev/github/SonarSource/sonar-scanner-gradle/.github/workflows/build.yml:100). Verify current published product support separately before promising a CLI range.

## Maintenance outlook

- **Plugin export:** lowest semantic duplication, but one more public plugin mode and a distribution/injection protocol. Every Gradle, AGP, or Kotlin plugin change still affects the build-side adapter. The CLI must track compatible plugin versions and export schemas. The current legacy and isolation branches add ongoing regression cost.
- **Built-in models:** least Sonar code inside the target build, but highest **semantic** duplication. Gradle can keep the Tooling API binary-compatible while IDEA/Eclipse model behavior, dependency resolution, generated sources, Android integration, and third-party IDE customizations change. Missing values invite convention guessing and special cases. A smaller first feature set is feasible if explicitly positioned as best-effort enrichment.
- **Custom model + shared contract:** more initial design and packaging work, but best path to one source of Sonar/Gradle semantics. Maintenance concentrates in the Gradle adapter and contract tests. Keep a small built-in-model fallback only if its weaker fidelity is visible to users and tests.

## Decision experiments before selecting an architecture

1. **Define parity.** On identical Java multi-project, nested, custom source set, Kotlin JVM, Android, and composite fixtures, compare the effective Sonar properties from the Gradle plugin with each candidate. Include `sonar.java.binaries`, main/test classpaths, report paths, generated sources, exclusions, module keys, skip behavior, and explicit overrides.
2. **Build a minimal export.** Add an export-only task or Tooling model backed by the plugin's project-local metadata and resolver data. From Scanner CLI, request it against a build **without** the Sonar plugin in its scripts and a build **with** an older pinned plugin. Verify no second engine starts, no unexpected producer tasks run, and no credentials enter the dump.
3. **Test the real compatibility matrix.** Use target wrappers 7.3, 8.x, 9.7+ (and older versions only if actually promised), their compatible daemon JDKs, configuration-cache reuse, Isolated Projects, offline dependency resolution, Windows paths, and a composite build. Check IDEA/Eclipse model requests under isolation before claiming that approach avoids isolation work.
4. **Measure cost and failure behavior.** Record cold/warm config time, downloads (including source jars), `buildSrc` work, daemon lifetime, cancellation, and behavior when only one subproject is broken. Ensure auto-config failure degrades predictably without hiding a failed analysis or silently dropping modules.

**Decision rule:** choose built-in models alone only if their documented limited property set satisfies the CLI product goal. If parity with Gradle-plugin analysis is required, prioritize the custom/export adapter and shared contract; using the existing `sonar` task itself is not an export solution.
